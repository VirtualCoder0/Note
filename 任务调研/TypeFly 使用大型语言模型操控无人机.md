# TypeFly：使用大型语言模型操控无人机

## 00 摘要

- 在涉及移动机器人(尤其是无人机)的实时交互应用中，LLMs 固有的顺序令牌生成过程在控制流程中引入了显著的延迟，即响应时间。
- 本文提出 TypeFly 系统，使用名为 MiniSpec 的新型编程语言及其运行时来减少计划生成时间和无人机响应时间，可以减少高达62%的响应时间，并提供更一致的用户体验。

## 01 引言

- PaLM-E、Instruct2Act、Large Language Models as General Pattern Machines、From Words to Flight、TidyBot 利用大语言模型及多模态模型来理解自然语言中的任务描述，并预定义函数调用或 Python 程序的形式生成无人机控制计划。
- 大语言模型的顺序 token 生成会导致推理延迟，该延迟与输出计划的长度成正比，从而增加了机器人控制的响应时间和完成时间
- 本文提出端到端的 TypeFly 系统，其核心思想是设计一种小型、专用的编程语言 MiniSpec，能让 LLM 以更高的令牌效率和成功率编写无人机控制计划

- 本文主要贡献：
  - TypeFly，一种端到端低延迟系统，通过大语言模型操控无人机完成以英语描述的复杂任务
  - MiniSpec，一种专为 LLM 设计的小型编程语言，旨在高效生成机器人任务计划。MiniSpec 具备一项特殊技能 probe，用于简化逻辑并提高计划的有效性。MiniSpec 还拥有一个特殊关键字 replan，用于处理诸如语法错误和意外情况等异常
  - 流式解释、流式生成和实时解释执行，用于 LLM 驱动的无人机控制，显著减少了无人机的响应时间。响应时间指的是从用户请求到无人机首次动作执行的持续时间。据我们所知，我们也是第一个在机器人控制中使用这种生成-执行模式的团队

## 02 背景

- 性能最优的大模型通常作为基于云的服务提供给用户

- **延迟**，调用远程大模型的延迟包括网络和计算两部分，仅输出五个 token 的计算延迟至少比网络延迟（几十毫秒）大一个数量级，延迟可以近似用以下公式表示：
  $$
  latency = a  * N_p + b*N_o +c
  $$
  其中 $N_p$ 和 $N_o$ 分别是输入和输出 token 的数量，c 是网络延迟和服务调度延迟。 在实际对 GPT-4 的测试中 $b \approx 2800 a$，即输出 token 的数量对总延迟有重大影响

- **响应模式**：LLM 通常支持两种生成响应的模式：批量生成和流式生成。批量生成一次性返回整个响应，这对于简短、精炼的答案或需要完整上下文进行进一步处理的情况非常有用。然而对于较长的输出，它可能响应较慢，因为用户必须等待整个响应生成完毕。在流式生成中，LLM 逐步生成响应，在生成过程中将部分响应发送给用户，提高了响应速度和用户参与度。TypeFly 利用流式生成和 MiniSpec 的设计来减少规划响应时间。

## 03 相关工作

​    以往利用 LLM 生成基于程序规划的系统大多使用 Python，TypeFly 是首个利用自定义语言来优化 LLMs 在机器人规划中的响应时间的系统。尽管大  多数公开的LLMs都是在 Python 的广泛语料库上训练的，且Python设计简洁，但它主要是为人类编写程序而设计的，事实是 Python 程序在token效率上并不高。MiniSpec 专为 LLMs 设计，对于相同的语义，平均使用减少30%的token。此外，使用Python可能会导致第三方库的意外使用或无限循环，这可能意外情况的出现，而 MiniSpec 禁止无限循环，并且目前没有现有的 LLMs 在 MiniSpec 库上进行过训练。

​    TypeFly 利用 MiniSpec 的异常处理机制 replan 来实现增量规划(§5.1.4)，这与机器人技术中广泛使用的完全在线规划相关，但更为高效。在线规划根据当前场景为计划的每一步生成一个计划，相比之下，TypeFly 中 replan 仅在必要时被调用。

​    TypeFly 的另一项关键创新是通过特殊技能探针(§5.2)让 LLM 参与计划的执行。与此相关的是，LLM-Planner: Few-Shot Grounded Planning for Embodied Agents with Large Language Models. 也通过让 LLM 在每执行几个动作后生成一个新计划，从而在整个执行阶段都涉及 LLM，这种方式既慢又昂贵。相比之下,TypeFly以一种新颖的方式：当面对视觉模型无法理解的人类语言请求时，它会介入提供响应。

## 04 系统概述

​    ==TypeFly 是一个低延迟、端到端的系统，它利用 LLM 通过自定义编程语言 MiniSpec 来控制无人机，使其能够高效地完成复杂任务并快速响应。在设计TypeFly时，我们旨在充分利用边缘计算资源和基于云的LLM能力，以成功处理用户下达的非预定义自然语言任务，同时保护用户隐私。==

![image-20250326232415921](https://raw.githubusercontent.com/VirtualCoder0/tuchuang/main/gongwei/20250327142238132.png)

​    如图1所示，一架配备运动控制器和视频捕捉功能的无人机，MiniSpec相关模块运行在本地边缘服务器上，以及一个云端的大型语言模型(LLM)。无人机通过 WiFi 连接将摄像头捕捉的画面发送至边缘服务器。用户，无论是人类还是语言代理，都可以观察实时视频反馈，并以自然语言向边缘服务器提供高级指令，即过程（1），称为任务描述。同时，本地服务器上的视觉编码器基于这些图像为其他模块提供场景描述API。边缘服务器通过调用 LLM 并执行机器人控制的解释功能这两个关键组件在生成有效且高效的 MiniSpec 中扮演着核心角色。首先，提示生成器向远程 LLM 发送一个提示，该提示包含 MiniSpec 的语法、任务描述、场景描述以及关于TypeFly的其他相关信息和示例，以帮助制定符合任务目标的可执行解决方案（2）。其次，MiniSpec 运行时负责解析和执行从远程LLM接收到的 MiniSpec计划（3）。当 MiniSpec 运行时在流模式下接收到远程LLM生成的令牌时（4），它将在生成并解析可执行语句后立即执行 MiniSpec 计划。同时，MiniSpec 运行时持续从远程LLM接收计划的后续部分。在计划解释和无人机控制（5）过程中，边缘服务也可能通过提示生成器（6）与远程 LLM 进行交互，通过执行特殊的系统技能探测以实现高效请求，并在 MiniSpec 中使用关键字 replan 进行异常处理。

- 系统可扩展性

  TypeFly 可移植到其他机器人平台: 只有部分系统技能(无人机控制和高层技能)是平台特定的，而 TypeFly 的其余部分，包括 MiniSpec、提示生成器和视觉编码器，都是平台无关的。

- 用户角色

  用户，无论是人类还是语言代理，都使用自然语言与 TypeFly 进行交互。用户提供任务描述，接收log输出，并在 TypeFly 执行任务时观察无人机的实时 视频捕捉。此外，用户可以随时终止执行。

- 视觉分析  

  我们选择结合 LLM 和轻量级视觉编码器，而非利用视觉语言模型(VLM)的最新进展。直接在边缘服务器上部署 VLM 会带来显著的计算开销和延迟，而在云端部署则因图像嵌入可能被逆向工程而引发隐私问题。我们的策略通过仅向云端发送基于语言的环境描述，降低了 LLM 服务成本并增强了隐私性。

## 05 MINISPEC —— 为 LLM 编写程序（计划）而专门设计的语言

​    与 Python 相比，MiniSpec 具有简洁且有限的功能集、简化的语法，以及强大且可预测的逻辑控制。这些特性使得流解释成为可能，它在降低响应延迟方面发挥着至关重要的作用。此外，MiniSpec 还支持异常处理机制，以应对代码执行过程中预期的重新规划和意外的错误。

### 5.1 语言设计

​    在 MiniSpec 语言中，系统技能和计划的语义被定义为一个遵循下列清单中规定的 Backus–Naur 范式(BNF)语法的 MiniSpec 程序，具有四个关键规则：

- 简洁且受限的函数调用:：MiniSpec 确保代码生成中生成较少的 token，同时防止意外的函数调用，从而提高效率和安全性。
- 强大且可预测的逻辑控制：MiniSpec 支持复杂的计划生成并防止无限循环，提供多功能且可靠的逻辑控制。
- 流式执行的简化语法：MiniSpec 提供了一套简化的语法集，支持自定义解析和流式执行功能，能够在接收到可执行计划片段时立即开始代码执行，从而减少响应时间并提高整体响应性。
- 异常处理：MiniSpec 提供了处理执行期间预期重新规划和意外错误的机制，提高了规划效率和准确性。

##### 5.1.1 简洁且有限的函数调用

​    我们设计 MiniSpec 的目的是确保在遵循有限可用函数集的同时用更少的 token 创建任务计划。具体来说，每个技能都有一个唯一的缩写skill_abbr，它是基于 skill_name 自动生成的。例如，iv 对应 is_visible，tc 对应 turn_clockwise。在执行计划时，只有有效的可调用对象（即系统技能和MiniSpec 关键字）才能被执行，从而防止潜在的安全问题和未定义行为。MiniSpec 中技能的使用遵循函数调用的语法（如上表所示），其中技能缩写对应于函数调用中的<函数名>。需要注意的是，较少的字符并不总是导致较少的标记。例如，根据 OpenAI 的 tiktoken tokenizer，“desc.” 使用两个 token，而 “description” 仅使用一个。然而,我们发现所有两个字符的单词总是使用一个标记。因此，每个技能的缩写被生成为最多 2 个字母字符的唯一标识。

##### 5.1.2 强大且可预测的逻辑控制

​    MiniSpec 支持条件控制和有界迭代(循环块必须具有固定的预定计数)，从而能够组合复杂的任务计划，同时保证所有操作都将在有限的步骤内终止。此外，MiniSpec的语法支持变量赋值，提供了状态操作的机制。因此，尽管由于缺乏对无限循环结构的支持，MiniSpec未能达到图灵完备性的标准，但它仍然具备相当的计算能力。

##### 5.1.3 流式解释的简化语法

​    MiniSpec 支持的流式解释功能意味着在 LLM 流式生成过程中，一旦接收到有效的代码片段，代码执行即可立即开始。我们通过维护一种紧凑且简单的语法来实现这一功能，该语法仅包括逻辑控制、变量赋值和可用的系统技能，MiniSpec 代码可以轻松被我们的解释器解析。这一功能使 MiniSpec 能够以最小的响应时间支持敏捷的机器人控制，从而提供更具吸引力和互动性的用户体验，并适用于实时应用。流式解释的细节将在5.3节中介绍。

##### 5.1.4异常处理

​    MiniSpec 支持使用特殊关键字 replan 进行异常处理，该关键字可通过 3 种方式使用：

- 云端 LLM 可以在已生成的计划中使用 replan 作为函数，来提高动态环境中的规划效率和准确性
- 用户可以定义自定义逻辑，在特定操作可能引起显著场景变化时触发 replan。例如，如果无人机旋转超过 180 度或向前移动超过10米，则可以触发重新规划。
- 每当在解析过程中发现语法错误或在执行过程中发生机械故障时，解释器将触发 replan 以寻找潜在的修复方案。

​    一旦在计划中遇到由解释器触发或由系统技能抛出的 replan，计划的执行将立即停止，并通知提示生成器向远程 LLM 发送新的规划提示，以重新生成一个新的计划。为了进一步说明当远程 LLM 在生成的计划中主动使用 replan 时的应用，考虑以下示例：给定任务“转身去找苹果”（在评估部分7中使用的一个任务），一个没有使用 replan 生成的计划可能是：==turn_cw(180);goto('apple')==。如果无人机和苹果之间存在障碍物，goto(‘apple’)命令将失败，导致任务失败。通过我们的设计，远程 LLM 可以首先生成一个计划：==turn_cw(180);replan==。replan 随后将根据更新后的场景生成新的计划，引导无人机绕过障碍物并到达苹果：例如==move_left(50);goto('apple')==。

​    当任务涉及的环境在初始规划阶段并不完全已知时，仅凭初始场景描述一次性生成整个计划可能既不高效也不准确。replan 函数允许远程 LLM 在多步骤任务中推理潜在场景变化，更好地适应环境变化，与单次离线规划方法相比避免了提前生成过多不必要计划的开销。更重要的是，它仅在必要时调用，与完全在线方法(每一步都进行更新)不同，在效率和可用性之间取得了良好的平衡。

### 5.2 系统技能

​    系统技能是一个代表系统能力的 MiniSpec可调用对象。它通常由人类创建并提供给LLM，以便在计划中使用。为了实现效率目标，我们设计了一个包括低级和高级技能的层次化技能集：低级技能对应于系统支持的可调用函数, 而高级技能则由其他技能和逻辑控制构建。所有系统技能都是阻塞的，并在其动作完成后返回。列表2展示了 Type-Fly 中技能实现的示例，技能附带一个表达性的 name 和一个 des，帮助 LLM  理解功能。低级技能具有最初级的行为：系统支持的带有参数的可调用函数，例如列表2的第3行。然而，如列表2的第15行所示，高级技能的行为包括一个作为字符串的 MiniSpec 程序。此外，与低级技能不同，高级技能不显式地接受任何参数；相反，它将从其 MiniSpec 定义中的位置参数推断实际参数

##### 5.2.1低阶技能

​    TypeFly 的低阶技能包括基础无人机控制、视觉工具、用户界面以及一项特殊技能。假设所有机器人平台都配备了摄像头，唯一与平台相关的技能是无人机控制技能。无人机控制技能是大多数无人机平台支持的基本操作，如 move_forward 和 turn_cw。视觉工具技能提供特定对象的详细信息，如目标对象的位置、尺寸和颜色，这些功能由YOLO等流行的计算机视觉工具支持。用户界面技能向用户展示文本或图像反馈。

​    MiniSpec 还具备一项特殊的技能探针，这对于 TypeFly 的能力和效率尤为重要，它通过在计划执行过程中调用远程 LLM 来实现。在计划中调用探针会向远程 LLM 生成一个包含 question (即探针的参数) 和最新场景描述的小提示。它指示 LLM 用最少的词语(通常为 1 或 2 个标记)回答问题，并返回答案以继续执行。这种技能在运行时高效地利用了远程 LLM 的常识推理能力，同时无需进行在线规划，即无需交替进行规划和执行操作。例如，给定任务“定位你身后的可食用物体”，如图 1 所 示，带有探针的计划可以向大模型 offload  “这里有可食用目标吗?” 任务的条件检查，并执行有条件的转向以搜索可食用对象，如列表3所示。在不使用探针的情况下，云端 LLM 将生成如列表3底部所示的计划，该计划列出了所有可能的可食用对象并逐一搜索。这不仅在计划生成上效率低下，因为它会导致更长的计划，而且也不完整，因为目标对象的列表是有限的。此外，在这种情况下，执行时间将根据场景中的实际对象而显著变化。

##### 5.2.2 高级技能

​    TypeFly 的技能集选择性地包含少量高级技能，以提高计划的成本效益，并简化云端 LLM 的编程工作。低级技能构成了 TypeFly 的全部能力。理论上来说，远程 LLM 可以仅基于这些低级技能生成计划。然而，这样的计划冗长且成本效益不高。在另一个极端，一个系统可以提供大量语义丰富的高级技能，将所有先前成功的计划全部转化为高级技能。由于整个技能集都包含在规划提示词中，拥有大量高级技能的技能集会增加云端 LLM 服务的成本。此外，我们的经验表明，添加过多的高级技能会导致 LLM 生成仅包含高级技能的计划，从而导致错误的计划。因此我们在上述两个极端之间取得平衡，TypeFly 包含了少量高级技能，如 scan(obj_name)、scan_abstract(description)、orienting(obj_name) 和 goto(obj_name)。这些技能被大多数任务广泛用于查找和与目标对象交互，将它们纳入高级技能集可以在规划提示中简化并提高计划质量，而几乎不增加开销。

​    列表4展示了 MiniSpec 中的一项高级技能 scan 及其等效的 Python 代码表示。scan让无人机以8个步骤旋转360度，检查给定物体是否存在。每当在循环中发现目标物体时，技能返回True；否则，无人机顺时针旋转45度。如果循环完成，技能返回False。通过 OpenAI tiktoken 标记器测量结果显示在 MiniSpec 中该技能仅需18个标记，而其 Python 等效代码需要41个标记。

### 5.3 MiniSpec 运行时

​    ==TypeFly 减少响应时间的关键因素之一是流式解释,它允许无人机在 LLM 仍在生成计划时就开始行动。相比之下，大多数工作采用在接收到整个计划后再开始执行的方式，在这里被称为正常解释。==

##### 流式解释 vs. 常规解释

​    如下图所示，在常规解释中，提示词生成器将提示输入 LLM，系统等待整个计划(蓝色条)接收完毕后才开始翻译和执行。因此，响应时间随计划长度变化，当系统被指示执行复杂任务时，可能导致响应性降低。相比之下，流式解释将计划视为流，通过 MiniSpec 的设计，我们的 MiniSpec Runtime 能够轻松识别可执行语句(下图中的蓝色块，本节稍后将详细说明)并尽快开始执行。这种设计减少了用户命令与机器人动作之间的等待时间，使控制系统更具响应性，更适合实时应用。LLMCompiler 在 LLM 解码期间采用了类似的任务级预取执行方法，以优化QA应用中的延迟性能，MiniSpec 和 MiniSpec Runtime 在语言级别支持这一特性，并提供了更广泛的适用性。

![image-20250327174001181](https://raw.githubusercontent.com/VirtualCoder0/tuchuang/main/gongwei/20250327174001217.png)

​    接下来,我们介绍如何通过 MiniSpec 语言设计(在5.1 节中介绍)与 MiniSpec 运行时的结合来实现流式解释。MiniSpec 运行时是一个解释器，能够同时接收、解析并执行 MiniSpec 计划。MiniSpec运行时包含两个线程，一个预处理线程负责接收流式 LLM 响应、解析并将 MiniSpec 代码片段格式化为Statements；另一个工作线程采用无限循环通过队列从线程队列中的第一个线程接收 Statements。

​    一个 Statement 代表一个 MiniSpec 代码块，它可以是一个函数调用、一个变量赋值、一个条件块或一个循环块。前两种类型是 **Elementary Statements**，例如上图中的 tc(180)，后两种类型是 **Composite Statements**，一个 MiniSpec 程序是一系列 Statements 的序列。每当一个 Elementary Statement 全部完成或一个 Composite Statement 部分完成时，它就被认为是可执行的，MiniSpec 运行时会将其发送到工作线程进行执行。

​    对于 Composite Statements，解析和执行因类型而异。条件 Statement 以条件开头（带有前导标记“?”），可能是子条件的交集和并集的组合。每个子条件可能涉及技能调用返回值与字面值的比较。一旦条件完全满足, Statement 将被发送到工作线程，而无需等待主体块（由 “{ }”包围）完全生成。当工作线程执行条件时，另一个线程将继续向主体块中添加 substatements。如果条件结果为True，工作线程将开始执行主体块。在极少数情况下，条件执行后主体块仍然为空。在这些情况下，工作线程将等待下一个可执行的Statement被追加到块主体中。

​    对于 Elementary Statements，过程是直接的。预处理线程接收到一个完整的 Elementary Statements 后，会将其发送给工作线程执行。工作线程只需在阻塞模式下调用系统技能（或进行变量赋值）。值得注意的是，在我们的应用中，大多数 Statements 的执行时间显著长于 LLM 生成和预处理所花费的时间。

## 06 实现

- 无人机：Tello（提供最高 HD720P/30 FPS 的视频流）
- 边缘服务器：Nvidia RTX4090、16核 RYzen 7950x、64G RAM（峰值消耗20%可用资源）
- 云端 LLM: OpenAI GPT-4
- 软件组成
  - 用户交互模块：TypeFly 用户通过 Web 界面与系统交互，用户可以通过该界面提供任务描述，观察无人机实时视频反馈，并阅读视觉编码器输出的场景描述。
  - 视觉编码器：视觉编码器基于 YOLOv8，可以根据无人机捕获的图像生成场景描述。
  - 提示词生成器：将用户的任务描述与系统描述及视觉编码器的当前场景描述相结合，然后生成提示词并发送至 LLM。
  - MiniSpec运行时：解释并执行由远程LLM生成的 MiniSpec 计划程序

##### 提示词生成器

- 采取长提示短输出策略，原因如下：
  - 为了低延迟控制目标，我们期望 LLM 仅生成必要的标记，从而最小化计划生成时间
  - 采用带有详细解释和指南的少样本提示提高准确率



##### 视觉编码器

- 视觉编码器采用YOLOv8，它生成一个可检测对象的列表，包含对象的类型名称和边界框。

## 08 结束语

​    在本文中，我们介绍了 TypeFly，这是一个允许无人机通过自然语言命令实现低延迟控制的系统。TypeFly 通过结合基于边缘的视觉智能、创新的自定义编程语言 MiniSpec 以及利用大语言模型(LLMs)的提示工程，实现了这一目标。通过一系列逐渐复杂的无人机任务，TypeFly 展示了其显著减少系统响应时间的能力，并通过高效的任务完成为用户提供更一致的体验。尤为重要的是，TypeFly 中探针的集成以及 MiniSpec 的异常处理机制(replan)显著提高了完成复杂任务的可能性。我们在 TypeFly 的使用过程中也发现了许多需要解决的挑战以及未来工作中值得探索的机会，例如：

- 对于需要全面理解场景和环境的更复杂任务，TypeFly 在缺乏历史观察记忆和环境建模的情况下显得力不从心
- TypeFly 中的交互方法每次都将完整的提示内容发送给LLM。对于不同的任务，只有场景描述和任务描述可能有所不同，这些内容占提示总长度的不到8%。
